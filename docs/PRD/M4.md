# Zippy Logistics — Milestone M4: Odoo Pipeline & Payment Webhook Router

## Objective
Wire the deterministic core to the outside world: Odoo 18 CE as system of record (order mirroring) and the Razorpay webhook ingress with idempotent dedupe, dead-letter handling, and lost-webhook reconciliation (WF-1 / WF-5).

## Entry Criteria
- M3 complete.

## A. Webhook Router (S6 / D-08)
- Endpoint: `apps/portal/src/app/api/webhooks/razorpay/route.ts` (public URL per D-08 — Vercel cannot reach internal hosts).
- Pure utils in `src/lib/webhooks/razorpay.ts`: HMAC-SHA256 verify against `RAZORPAY_WEBHOOK_SECRET`, event-type mapping.
- Flow: verify signature → upsert `webhook_events` (idempotency_key = provider event id; unique → duplicate delivery is a no-op) → enqueue `agent_task(process_payment_event)` for `payment_settlement` → **ACK 200 immediately** (gateway SLA).
- Failures after ACK are retried via dead-letter sweeper, never via gateway redelivery assumptions.

## B. Sweeper & Reconciliation Jobs (Migration 11 SQL)
| Job | Function | Behavior |
|---|---|---|
| WF-5 dead-letter | `sweep_dead_webhooks()` | webhook_events unprocessed with attempts ≥ max (5) and last error older than 10 min → mark `error_message='DEAD_LETTERED'`; separate `revive_dead_webhooks(limit)` resets for manual replay |
| WF-1 reconciliation | `stale_processing_payments(p_minutes)` | payments stuck `processing` > threshold + their gateway ids → candidate list the worker re-checks upstream |
| Mirror control | `mark_odoo_synced()/mark_odoo_failed()` | order-level odoo refs update (`odoo_sale_order_id`, `odoo_invoice_id`, `odoo_sync_status`) |

## C. Odoo 18 CE Pipeline
- `workers/odoo_client.py`: JSON-RPC over httpx (`/jsonrpc`, authenticate → execute_kw), no ORM magic; capability-gated (`assert_can_call_external('order_management','odoo')`).
- Handler `push_order_to_odoo`: create/find `res.partner` by email → `sale.order` mirror of the order payload → persist refs + emit `order_event_log('odoo_sync_succeeded')`.

## D. Worker handlers wired to kernel
`payments.py.process_payment_event` — verifies payment.completed maps to `transition_order(... 'inventory_confirmed')` idempotently then enqueues odoo push. All handlers receive an injected `Db` port (test fakes in pytest; SupabaseTaskSource in prod).
